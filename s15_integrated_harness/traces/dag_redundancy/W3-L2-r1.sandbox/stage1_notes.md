# Stage 1 — Runtime behaviours described by s15_integrated_harness/GLOSSARY.md

1. The lead loop tracks the running user request as first-class state (`active_user_request`), appends scheduled cron lines ("Run scheduled task: …") to it when jobs fire, and preserves it as the Authoritative request — the only field allowed to carry instructions after compaction.
2. Every lead turn runs through one shared control loop, `agent_loop`: inject scheduled cron prompts and background notifications, emit a todo reminder, run the compaction pipeline (`prepare_context`), refresh context and tool pool, then call the model.
3. The agent loop stops only when the model response contains no concrete `tool_use` block (checked by `has_tool_use`, never `stop_reason` alone); otherwise it dispatches the requested tools and appends their results as one user message, repeating.
4. `async_event_loop` (the "lead-events" daemon thread) polls every second and, when the cron queue has fired, the lead's inbox has team events, or background work finished, wakes the lead by rerunning `agent_loop` inside `traced_lead_turn` with a combined "cron+team+background" trigger.
5. A `bash` call marked `run_in_background: true` is moved into a `background-<id>` daemon worker thread with its own process session; the model immediately receives a placeholder tool_result and the real output arrives later as a `<task_notification>` user message.
6. Compaction (`prepare_context`) runs as a cheap-first layered pipeline: `tool_result_budget` persists oversized tool outputs of the latest message to `.task_outputs/tool-results/`, `snip_compact` archives old message ranges to `.transcripts/` keeping head 3 + tail 46, `micro_compact` turns the oldest consumed tool results into saved-path markers (keeping the 3 newest), and `fit_tool_results` replaces the largest results with 1000-char persisted previews.
7. `compact_history` performs full model summarization into one `[Compacted]` message and fires only while the estimated size (`estimate_size`, `len(json.dumps(...))`) still exceeds `CONTEXT_LIMIT` (512000 chars, i.e. 128k tokens at 4 chars/token); two extra entry points are the `compact` tool (special-cased in `agent_loop`) and `reactive_compact` on prompt-too-long errors (at most once per turn).
8. Cron jobs (a 5-field cron expression plus prompt) are stored apart from conversation history; the `cron_scheduler_loop` daemon ticks each second and enqueues due jobs deduped by a per-minute `_last_fired` marker, and `agent_loop` consumes the queue as `[Scheduled]` user messages.
9. `durable` cron jobs persist to `.scheduled_tasks.json`, and one-shot jobs use `pending_delivery` with `acknowledge_cron_jobs`/`restore_cron_jobs` to guarantee at-least-once delivery.
10. `RecoveryState` + `with_retry` wrap every model call with up to 3 attempts: 429/529 errors are retried with exponential backoff (500 ms base, ×2 per attempt, capped at 32 s, up to 25% jitter), and two consecutive 529s switch to `FALLBACK_MODEL_ID` if configured.
11. `agent_loop` recovers `max_tokens` stops with one 8000→16000 escalation followed by up to 2 continuation prompts, and recovers prompt-too-long errors with a one-time `reactive_compact` detected by `is_prompt_too_long_error`.
12. A `harness_decision` trace event is emitted at every control-flow branch — `dispatch_tools`, `continue` (reasons `prompt_too_long`, `max_tokens`, `compact_tool`), and `stop` (reasons `no_tool_use`, `model_error`, exhausted recovery) — carrying `decision`/`reason`/`action` so a trace faithfully records the loop's control flow.
13. `trigger_hooks` executes the `HOOKS` registry callbacks (UserPromptSubmit, PreToolUse, PostToolUse, Stop) in registration order and returns the first non-`None` result; for PreToolUse that returned string becomes the denying tool_result.
14. Built-in hooks run as extension points outside tool handlers: `user_prompt_hook` on prompt submit, `permission_hook` + `log_hook` on PreToolUse, `large_output_hook` on PostToolUse (warns above 100000 chars), and `stop_hook` counting tool results.
15. The integrated harness is a single Python process combining tool dispatch, permissions/hooks, todo and task board, teams, worktrees, MCP, compaction, background and cron, memory and skills, and tracing — one shared `agent_loop`, one traced Anthropic client, and file-backed state under the working directory.
16. The lead agent (`agent-root`) runs on the main thread and is the only thread allowed to ask interactive permission questions — `permission_hook` fails closed for any other thread.
17. `connect_mcp` registers a server (in-process mocks for real transports) and `assemble_tool_pool` merges its tools under normalized `mcp__{server}__{tool}` names with collision detection; authorization comes from the host policy table (default `confirm`), never from server-provided descriptions, and `MCPClient.call_tool` bounds exceptions to `MCP error: …` strings.
18. Each turn `update_context` calls `load_memories` (traced as purpose `memory_recall`) to supply the memory catalog and relevant records for prompt assembly, and at turn end `remember_after_turn` runs `extract_memories` and, when new records are stored, `consolidate_memories`.
19. The `task` tool spawns a one-shot subagent: a synchronous nested tool loop (up to 30 rounds, five filesystem tools only) with an isolated `messages[]` and its own system prompt that returns only the last assistant text to the parent, traced as `agent_create`/`agent_start`…`agent_end` with `agent_kind="one_shot"`.
20. The permission boundary is layered on the raw `tool_use` block before dispatch: bash commands are screened against a substring deny list (`rm -rf /`, `sudo`, …) then require an interactive `Allow? [y/N]` answer (main thread only; asynchronous turns fail closed), `read_file`/`write_file`/`edit_file` paths must resolve inside `WORKDIR`, `mcp__*` tools follow their host policy, and a string returned by the PreToolUse hook short-circuits dispatch as the denying tool_result.
21. Plan gates (`required`/`pending`/`approved`/`rejected`/`not_required`) hard-block `bash`, `write_file`, `edit_file`, and `complete_task` until the lead approves a submitted plan, and `advance_assignment_version` re-arms the gate to `required` whenever a new assignment is claimed so old approvals never leak into new work.
22. `assemble_system_prompt` rebuilds the system prompt from live context every turn in fixed section order (identity, tools, tasks, teams, workspace, memory, compaction), followed by the current time, the skills catalog, and — when present — the memory catalog, relevant memory records, and connected MCP servers, joined by blank lines.
23. `scan_skills` reads `skills/<name>/SKILL.md` packages (YAML frontmatter `name`/`description`) into `SKILL_REGISTRY` at startup; only the name-plus-description catalog enters the system prompt while full skill content is fetched on demand through the `load_skill` tool.
24. Task board records (`.tasks/task_*.json`) are protected by an in-process `RLock` plus a cross-process `flock` with atomic tmp+rename writes; `update_task` adds `blockedBy` edges only while a task is pending and unowned (rejecting self-dependencies, missing targets, and cycles), `claim_task` atomically verifies all blockers (`can_start`), sets owner and `in_progress`, and binds the owner's cwd lease, and `complete_task` requires ownership and a cleared plan gate.
25. Teammates run in `teammate-<name>` daemon threads with a reduced tool pool (five filesystem tools plus `send_message`, `submit_plan`, `list_tasks`, `claim_task`, `complete_task`) and a MessageBus inbox; filesystem tools resolve cwd through `assignment_cwd` and fail closed until a task is claimed, the final text is delivered to the lead as a `result` message, and an idle teammate waits on the bus before auto-claiming the next ready task via `claim_next_task`.
26. Per-tool_use dispatch order is: the `compact` special case, PreToolUse hooks (which can deny), background dispatch for marked bash calls, the handler inside a `tool_execution_start`/`tool_execution_end` span via `call_tool_handler`, then PostToolUse hooks — with all results plus newly finished background notifications appended as a single user message by `build_user_content`.
27. Each trace event is one JSON object per line in `traces/run_*.jsonl`, emitted by `TraceRecorder.emit` with a fixed envelope (schema version 1.0, UTC timestamp, `monotonic_ns`, `elapsed_ms`, `run_id`, `turn_id`, `event_id`, event name, agent identity, `span_id`/`parent_span_id`, causal fields, thread info, redacted `data`); the file is opened mode 0600, appended line-buffered, and flushed per event.
28. The trace runtime defaults to `NullTraceRecorder` so importing the lesson never creates files, while the CLI entry point builds a `TraceRecorder` from `HARNESS_TRACE*` environment variables; `wrap_client` turns every `messages.create` into a `model_request` → `model_response`/`model_error` span, `contextvars` scopes (turn, agent, model purpose, span) with `capture_context`/`restore_context` keep worker-thread events attributable, and `span()` pairs start/end events by `span_id`, recording `duration_ms` and capturing exceptions as error data.
29. `trace_stats.py` is a read-only, directory-wide consumer of `traces/*.jsonl` that first validates every line against the trace envelope (warnings for schema drift, `run_id` changes, missing `run_start`/`run_end`), then aggregates model calls/models, stop reasons, token totals from `model_response` usage, tool-name frequency, and error/retry counts, exiting 1 if any malformed line is found.
30. `create_worktree` binds a real Git worktree under `.worktrees/<name>` on branch `wt/<name>` to exactly one pending, unowned task after name, Git, and registry validation; claiming that task makes the worktree the owner's cwd (`assignment_cwd`/`task_worktree_cwd` fail closed on broken bindings), and removal stays host-owned — it requires a completed bound task, no active cwd leases or running background commands, and a clean tree, and it always retains the branch.
