1Harness architecture

One loop, three nested scopes: a goal spans turns, a turn runs rounds, and a round is prepare → call → check

Terminology check. turn = one lead activation, traced as turn_start … turn_end (code.py:3669). round = one iteration of the loop: the s15 and s16 READMEs say "next round" / "each round", and spawn_subagent keeps a rounds counter with a 30-round cap (code.py:2168); the code's own comment calls the same iteration a "cycle" (code.py:3472). Either word is fine; "round" is the repo-wide one. /goal exists only in s17, whose max_turns confusingly counts model calls. Teammate shell: denied off the main thread when the runs were made; HEAD now auto-approves read-only commands.

2Adaptive dependency graph

The task board is a DAG the lead grows while the team runs: nodes first, edges second, readiness re-evaluated at every completion

How it is created

  • Phase 1, nodes. create_task writes .tasks/task_<id>.json: random runtime id, pending, no owner, empty blockedBy.
  • Phase 2, edges. update_task(addBlockedBy=[ids]) with the returned ids. Sibling tool calls in one response cannot see each other's ids, so edges come after nodes.
  • Guards. Target pending and unowned; dependency exists; no self-edge; a depth-first walk rejects cycles; edges are only ever added. Only the lead holds update_task. The Qwen lead hit board guards 9 times: 2 edge updates on already-claimed tasks, 7 spawns whose task was claimed or blocked.

How it evolves

  • State machine. pending → in_progress → completed; can_start only when every blocker is completed.
  • Claim is atomic (RLock + cross-process flock), one in-progress task per owner, and binds the owner's working directory.
  • Complete unblocks. complete_task needs ownership and a cleared plan gate, then reports the tasks that just became ready.
  • Idle teammates re-bind. Every 2 s an idle teammate auto-claims a ready task; a dead teammate's task goes back to pending. Qwen run: 18 of 43 claims were auto-claims, and one task had 4 owners after three 262k-token deaths.
  • The lead keeps adding. Waves 2–9 all came from lead-events turns reacting to team results (4 lead turns in all): the graph is grown, not declared up front.

Code (s15 code.py): create_task :285 · update_task :324 · can_start :402 · claim_task :436 · complete_task :475 · release_teammate_assignment :646 · claim_next_task :1374. Nothing reopens a completed task: in both X2 runs the lead re-created its finished tasks as a second wave; run 1's idle teammates auto-claimed them within a second, run 2 spawned new teammates after shutting the first wave down.

Lead: repeats because the harness forgets

A 50k-char compaction budget evicts a read after a median of 5 calls (X3); 82% of lead re-reads follow a compaction shrink. The lead extracts slices with grep, so its copies are partial and transient.

Teammates: repeat because the harness isolates them

No shared history and no shell off the main thread, so each teammate pages through the whole shared file and keeps every window forever. 95% of their reads hit a file another teammate had already read.

Where the identical bytes are

Identical reads are 3% of teammate reads by count but 66% by bytes: whole-file reads by a second agent. With disjoint files (X5) duplication is exactly zero, so it scales with task overlap, not team size.

Slices within one teammate are nearly disjoint (168 teammate reads of code.py in X2 run 2 used 162 distinct windows); across teammates the same lines are duplicated: each teammate holds 1.0–1.3 copies of code.py, the team 4.3× (X2 run 1) and 6.8× (run 2).

6Result · the lead

A 50,000-char harness budget makes the lead forget: raising it to 200k removed every re-read and cut wall time 5×

Mechanism

  • CONTEXT_LIMIT = 50000 chars (about 12k tokens) is a harness constant (code.py:99), not an API limit; a tenth of the model's window.
  • Once history exceeds it, micro_compact replaces every consumed tool result but the 3 newest with a saved-path placeholder; a read survives a median of 5 calls (max 11).
  • With the default limit, the lead read the s13 README 8 times and the s08 README 6 times; all 53 re-reads came after a history shrink (88 shrink events, 0 summary compactions).
  • 82% of all lead re-reads across runs followed a compaction shrink; in X1 the lead re-derived findings with fresh greps after a summary compaction ("let me re-verify").
  • The one-shot pattern duplicates too: in X4 the lead re-read the exact 21,821-char file its subagent had just summarised, because the child returns text only.

For this workload the default budget is counter-productive: 14× fewer calls and 5× faster with no loss in quality.

Answers questions 1 and 6 for the lead. Compaction pipeline: tool_result_budget → snip_compact → micro_compact → fit_tool_results → compact_history, run in prepare_context() before every model call.

7Result · the teammates

Teammates load whole files, keep every window, and carry finished tasks into the next one until the provider rejects the prompt

Whole files, incrementally

  • When these runs were made, shell was denied off the main thread, so a teammate could not grep: it paged with offset/limit. All 9 X2 teammates reached at least 99% line coverage of the 3,710-line code.py; the lead with grep covered 32–44%.
  • In the controlled runs 15 of 16 teammate-file pairs reached at least 90% coverage; the one partial case was a 69% paged read of a peripheral file (s09 code.py).
  • Paging costs one model call per page, and every window is appended verbatim and never removed, so the whole file ends up in context either way.

Never released

  • Teammates have no compaction: prompts reached 76–82k tokens in X2 and file content was 64–78% of their request bytes.
  • Provider cache entries eventually expire (a probe saw a small prefix drop between 300 and 600 s idle) and never transfer to another agent, so nothing is "freed" by the harness and nothing is reused across teammates.

Answers questions 2, 3 and 5. One-shot subagents are the exception: their list is local to spawn_subagent and dropped when only the final text returns. The report counts five 262k deaths (error notifications the lead received); the trace shows six rejected teammates. HEAD now auto-approves read-only shell for any thread (968a33c), but 10 of the 16 commands teammates tried would still fail closed.

What this means

  • Reuse the provider can exploit is where the harness spends the least effort: teammates get ~90% with zero support.
  • The lead's carefully compacted prompt gets ~17% because micro_compact, snip_compact and summary compaction rewrite the prefix every call.
  • The cache saves compute, not context: the whole file still sits in every teammate's window.

Answers question 4 and the cache half of question 3. The lead's 17% is the aggregate over 495 lead-side calls (5–28% per run). KV states depend on position and prefix, so no hosted API can reuse a file window across contexts; only a harness-level scheme (fixed blocks, pointers, a shared pinboard in the prefix) can.

Prefill ~2,400 tok/s, decode ~54 tok/s; a cached token costs 24% of an uncached one. A whole 143k-char file costs ~15 s of prefill once; a 2,000-token answer costs ~37 s of decode every time.

The real levers

  • Fewer model calls. X3: 100 → 7 calls cut wall time 808 → 168 s (−79%).
  • A cacheable lead prefix. The X3 lead spends 48% of its model time on uncached prefill; teammate-like hit rates would save ~265 s against 34 s from skipping re-read content.
  • Less coordination chatter. X2 runs spent 2,000–2,400 s of teammate time on decode and hit the 1,500 s ceiling.
  • The provider cache already skipped ~1,175 s of prefill in X2 run 2 (3.66M of 4.0M teammate prompt tokens were hits); without it teammate time would be 25–36% higher.

Outer bound if repeated windows were also removed from context (pointer instead of bytes): about +240 s on top of the 95 s in X2 run 2 (~335 s, ~10% of teammate model time). Caveats: one pooled fit for a hosted model with network included, and per-kind fits diverge; line-level "repeated" is the most generous count, so these are upper bounds.

10Conclusion

File-read repetition in s15 is structural, and the remedies are harness-side, not model- or API-side

What we found

  • The lead re-reads because a 50k-char harness budget evicts what it read (82% of re-reads follow a compaction shrink; a 200k limit removed them all).
  • Each teammate re-loads and permanently keeps the whole shared file because it has no search tool and no context reset; finished-task history rides along into the next task (35% of prompt tokens in the Qwen run, six contexts killed at 262k).
  • The provider's prefix cache hides most of the teammates' cost (90% hits) but almost none of the lead's (17%), because every compaction step rewrites the prefix.
  • Skipping the prefill of repeated file content would recover only 1–3% of teammate model time: the cache already absorbs most of it, and latency is dominated by decode and call count.
  • Duplication scales with task overlap, not team size: three teammates on one file tripled it; three teammates on three files duplicated nothing.

Harness-side remedies

  • A token-based budget near the model's real window instead of 50,000 chars.
  • A stable, cacheable lead prefix: move Current time out of the system prompt, batch micro_compact, reuse the snip_compact marker, add cache breakpoints.
  • Task-boundary resets for teammates: keep the assignment plus a short summary, drop the finished task's history.
  • A locator tool or a shared file pinboard so teammates search instead of paging, and one prefill serves the whole team. Read-only shell for teammates has since landed on HEAD (968a33c).

The next question is therefore not "how do we skip repeated prefill" but "where should each agent's KV cache live, and for how long".

11Prospection

Next: treat the team's KV cache as a managed memory hierarchy, with the lead's hot cache first and finished-task history last

Hot · the leadGPU memory, pinned
Give the lead's prefix priority. The lead gets 17% hits and spends 48% of its X3 model time on uncached prefill; teammates get 90% for free. Its working set is small (~8.5k prompt tokens per call against ~38k for a teammate), so once its prefix is stable it is the cheap one to keep resident, even if teammate entries must be evicted or demoted.
Warm · working teammatesshared, deduplicated
Share one cache across teammates reading the same file. 95% of teammate reads hit a file another teammate had already read; code.py was sent ~44 and ~103 times in X2. Nothing is shared today: every teammate's first call has zero cached tokens because its prefix opens with its own name and role. A pinboard block placed identically before the name would let one prefill serve the team.
Cold · idle or waitinghost DRAM
Keep an idle teammate's KV instead of losing it. A probe saw a 4.6k-token prefix expire between 300 and 600 s idle, yet in X2 run 1 71–82k-token prompts were still cached after 424–747 s: retention is provider policy the harness cannot see or control. On a self-hosted engine (vLLM blocks) it could offload to DRAM at IDLE and reload at claim.
Discard · finished tasksreset at task boundary
Distinguish and drop the unnecessary cache. A teammate's messages are never reset (code.py:1651 / 1789): 35% of Qwen teammate prompt tokens were finished-task history, six contexts died at 262k, and X2 run 1's second tasks started with 71–82k tokens of history. Since 16 of 22 later-task reads re-opened earlier files, a task-boundary reset should keep file pointers (the pinboard) and drop the rest.

Proposed experiments

  • Stable-prefix lead: no timestamp + batched micro_compact + reused snip marker; measure lead hit rate (target teammate-like 85%+) and X3 wall time.
  • Pinboard prefix: put the shared file in an identical block before each teammate's name; check that the second teammate's first call reports cached tokens, and count prefills of code.py (baseline ~44 / ~103).
  • Task-boundary reset: reset teammate messages to assignment + summary on complete_task; re-run the Qwen-style multi-task load and check prompt growth, 262k deaths, and answer quality.
  • Re-run X2 on HEAD: read-only shell is now allowed for teammates (6 of the 16 commands they tried would pass); measure how much whole-file paging disappears.
  • Tiered KV on vLLM: first enable prefix caching and cache metrics on the vLLM path (the current recipe has neither), then pin the lead's prefix, offload idle teammates' blocks to CPU memory, free finished-task blocks; measure cache pressure and per-call latency.

Assumption to state up front

Against a hosted API (z.ai) the harness controls only the bytes it sends: prefix stability, resets, pinboards, keep-alive calls. Eviction priority, offload to DRAM and selective discard need the self-hosted vLLM path, and nothing yet measures provider cache pressure, so the first step there is instrumentation.
