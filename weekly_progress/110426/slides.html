5Topic 23 · controller screen · Nov 2–3

The controller agrees with a reference rule in replay, but acts on metrics over a minute old

  • Replay: the controller's K agreed with a reference rule 94–98.5% of the time.
  • Live in pair 3, K swung 6–32 for 144 min, then held at 20.

Controller: a Qwen call every 60 s that reads the GPU's metrics and calls set_session_limit(K). Its snapshot covers the minute before a round; K changes when the call returns. c1–c4: prompt versions, each adding to the one before. Reference rule (screen_prereg.md): lower K when the active sessions' contexts pass 90% of the KV cache, or the prefix hit rate is under 50% with preemptions or requests waiting for KV; raise it when sessions wait at the gate and the next one's context would still fit in 80%; else keep. Sources: 23 README, S2 and S4; screen.md; runs/agate/controller.jsonl.

6Topic 23 · result: throughput

Only offloading every request raised throughput clearly, and only in tokens/s

  • lmc_all reloaded 38% of prompt tokens from DRAM: tokens/s 1.21×, clear; requests/h 1.09×, not clear.
  • No setup where the model decides clearly raised throughput; gate8 cut requests/h to 0.66×.

Throughput: vLLM's counters over the window with all 32 agents running (81–170 min), minus the harness's own calls (agate's controller calls). Tokens/s: prompt tokens (96% of it), cached or computed, plus generated ones; requests/h is closer to the agents' progress. Intervals from 8–17 ten-minute blocks; one run per setup. Sources: 23 README, Results; data/tables/et.md.

8Topic 23 · result: task time

Gated tasks took 10–26 minutes longer on average; no setup made the median task clearly faster

  • Fixed gates cut working time 29–49% but added more at the gate; agate only added gate time.
  • wait's tasks spent 331 s in the wait tool, yet ran 240 s shorter on average, about the A/A gap.

Task: one task's agent phase, start to end. Working: model calls and tools; the gate and the wait tool split out (et.json). wait's tasks made fewer calls (37.7 against 43.1; none_r2 45.3), so per call the wait tool took what the server saved. Gated tasks hit the limit less (11–21 against 25 and 31). Pass rates 71–78%, no difference clear. Sources: 23 README; et.md.

10Topic 20 · merge vs reorder

Merging could remove a quarter of the calls; overlapping tool time has little to work with

  • Folding each chain of independent rounds into one call removes 28% and 25% of lead calls.
  • Only 4.3% of Pro and Terminal-Bench tool seconds sit beside an independent next call (≤ 1.2% of trial time).

Merge: fold a chain of rounds, each producible while the earlier results are pending, into one response. Reorder: send the next call while the previous tools still run. Both gates and the 10% floor were frozen before the analysis. Pages 10–11 use the same 58 Pro + TB trials: 14.99 h of model + tool time, 4.02 h of it tools. The README's ceiling (≤ 6.4%) used the wider planning sample's tool share (Pro 41.6%, TB 46.4%). Split by the next round: post hoc, this deck. Sources: 20_round_dependency/README.md, S4–S5; census.md.

11Topic 21 · precautionary work · Oct 30

Asking MiniMax to front-load long commands barely moves it

  • Ceiling: merging up to the long commands removes at most 9.1% of calls, even with full compliance.
  • The front-load line: 9.9% early issue vs 4.4% for a neutral line; the bar was +15 points.

Long command (heavy round): ≥ 1 s of tools. Merge every chain: page 10's Pro 33% and TB 18% together. Time saved: share of the 58 trials' 14.99 h; at saturation none of it raises throughput. Valid early issue: at an earlier call, the reply issues the heavy command together with every earlier step it depends on. From your 10-29 idea: foresee congestion, ask for CPU-heavy work. 13Takeaways

Takeaways

  • At a steady load, the wait tool took about what each call saved; no throughput gain.
  • On Qwen, gates slowed tasks 10–26 min; only offloading every request to DRAM raised tokens/s (1.21×).
