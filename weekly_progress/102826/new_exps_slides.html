2Topic 18 · agent waiting · setup

Can an agent relieve a crowded server by pausing itself?

SetupQwen3-32BvLLM 0.312× H100 per server8 / 16 / 32 users90-min windowspre-registered
  • Many agent sessions share one server; once KV memory fills, evicted prompts are recomputed.
  • Three deciders tried: the model with a wait tool, a fixed harness rule, and the server's gate.

KV cache: the server's stored state for a prompt's tokens; a hit reuses it, an evicted prefix is recomputed (re-prefilled). Source: 18_harness_wait/README.md.

3Topic 18 · result

Pausing helps only when the harness decides

  • With a live status and a wait tool, the model reached 0.7–0.9× the no-wait throughput.
  • A fixed harness rule on the same status reached 1.8–2.8×; the server's gate 3.2–3.8×.

Throughput: the lead agent's work calls (model calls that do work, not waits) per hour. The turn-start run is exploratory, not pre-registered. Sources: 18_harness_wait/README.md (S3, Exploratory); s15_integrated_harness/hold_runtime.py.

4Topic 18 · why the model fails

The model waits in loops, and each wait is another model call

  • 81–99% of its wait-only rounds came in runs of ten or more, barely tracking the status.
  • Each wait call first re-prefills the evicted context: 22–32% of GPU time at 16+ users.

Wait-only round: a model reply whose only tool call is wait. The model chose each wait's length (median shown); the tool slept exactly that long. Source: 18_harness_wait/README.md (S3, H1).

5Topic 18 · follow-ups · measured, then simulated

Prompts lose their cache while queued; only capping active sessions fixes it

  • Calls arrive with 87–94% of their reusable prefix cached, but keep only 1–5% after queueing.
  • Simulated: reordering requests gives 0.9–1.7×; capping active sessions, as the gate does, gives 3.7×.

Why: first-come admission plus least-recently-used eviction evicts exactly the prefix needed next. Source: 18_harness_wait/FOLLOWUPS.md (§1, the simulator).

7Topic 19 · result (main run)

The stronger model ignores the signals; only the gate helps

  • Main run: 3 pacing calls in 21,081 lead calls; its reasoning mentions the signals only twice.
  • Only the server's gate helped: 1.42–1.44× completed turns per hour; the two model setups reached 0.92–1.04×.

Pre-registered: the pass/fail rules were written and hash-frozen before the main run, so the results could not steer them. One 90-min run per setup and load. Sources: 19_efficiency_signals/README.md (Short answer, S3), prereg.md.

8DGX Spark · exp01 · the memory system

On the Spark, CPU and GPU share one memory, through two GPU paths

SetupGB1020 Arm cores + Blackwell GPU128 GB LPDDR5xno hardware counters
  • One 128 GB memory at 273 GB/s peak serves 20 Arm cores and a Blackwell GPU.
  • GPU-allocated memory streams at ~255 GB/s; CPU-allocated memory caps near 165–170 GB/s, shared with the CPU.

ATS: the GPU reaches CPU-allocated memory through the CPU's page tables. Sources: exp01 results/REPORT.md (§1, §5), followups/FOLLOWUPS.md (§0, §2.2).

9DGX Spark · exp01 · CPU–GPU interference

GPU traffic slows the CPU long before memory saturates

  • Each GB/s of GPU traffic costs the CPU 0.29% of its bandwidth; p99.9 latency rises 4–5× at 100 GB/s.
  • At saturation the trade is concave, not constant-sum; a three-parameter model predicts it with 1–4% mean error.

Constant sum: what the GPU would get if CPU + GPU bandwidth always added up to the GPU-alone 255.5 GB/s. Sources: exp01 results/REPORT.md §5 (tables fig3_grid_medians, fig3_frontier_cudamalloc); followups/FOLLOWUPS.md §0.

10DGX Spark · exp02 · vLLM serving

A decoding vLLM server fills the memory from its first user

SetupQwen3.8-27B (48 DeltaNet + 16 attention layers)BF16vLLM 0.3224 GiB KV pool1–64 users
  • Each decode step streams all 51 GB of weights: 233 GB/s, 85% of peak, from one user on.
  • CPU readers beside it keep 27–43% of their bandwidth; a 12-core CPU writer cuts decode to 37–43%.

DeltaNet state: the hybrid model's fixed-size memory per user, read and written every step. Source: exp02 REPORT.md §3–§5 (decode-heavy load: 128-token prompts, ~1,024-token replies).

11DGX Spark · exp02 · where to put spare memory

On the Spark, give spare memory to the GPU's KV pool, not a CPU tier

  • On the Spark, CPU and GPU memory are the same chips, so a CPU KV tier copies DRAM to DRAM.
  • Given to the GPU's KV pool instead, the same 12 GiB ran 63 requests, not 51, and ended preemptions.

KV pool: GPU memory vLLM reserves for prompts' cached attention state. CPU KV tier: vLLM's option to copy that state into CPU memory. Preemption: vLLM evicts a running request and recomputes it later. Source: exp02 REPORT.md §8.6.

12DGX Spark · exp02 · capping vLLM's GPU cores

Capping vLLM's GPU cores protects CPU services that share the memory

  • While vLLM decodes, CPU memory accesses wait behind GPU traffic; a CPU lookup service's p99 rises 45×.
  • Capping vLLM at 14 of 48 SMs cuts its memory pressure: that p99 falls 6–24×; decode slows 8–18%.

SM: one of the GPU's 48 compute units. MPS: NVIDIA's multi-process service, used here to cap vLLM's SMs. Lookup service: a CPU key-value store answering 16-key reads. Sources: exp02 REPORT.md §4, §7.2; raw/tables/levels.csv.

13Takeaways

Takeaways

  • Pausing agents relieves a crowded server only when the harness or server decides; neither model used the signals well.
  • On the Spark, decoding saturates the shared memory; CPU work pays in bandwidth and tail latency.
