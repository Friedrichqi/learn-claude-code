### Prefix caching and the rolling snip

s15 caps a conversation at 50 messages. Once a run passes that, every lead call cuts the middle again and rewrites the archive marker. Everything after the first three messages moves position, so vLLM's prefix cache cannot reuse it, although that tail's content is unchanged. This is the edit that shift and EPIC can act on. ## 5. Deviations from the official protocols

- **GAIA not run.** The user dropped it on 2026-10-12. The adapter path (web tools, answer file, official `question_scorer`) exists and passed its oracle check on 3 tasks.
- **30 tasks per benchmark, 3 trials each** (the plan allowed 25-40). Docker's root disk (~33 GB usable on a shared machine) limits how many SWE-bench / Pro task images can be present at once, which made it the throughput bottleneck. Terminal-Bench's leaderboard asks for 5 trials.
- **Terminal-Bench: 4 disk-heavy tasks replaced**: compile-compcert → sqlite-with-gcov, mteb-retrieve → query-optimize, count-dataset-tokens → pytorch-model-recovery, install-windows-3.11 → configure-git-webserver. Each writes up to its 10 GB storage limit into the container layer, so it can only run one trial at a time. Each replacement is the first reserve task of the same category and difficulty.
- **SWE-bench Pro: 4 protonmail/webclients tasks replaced** (19.6 GB images) by reserve tasks of the same language. Agent without network through Harbor's egress sidecar, as in Scale's protocol; local Docker instead of Modal. The V2 task statements specify interfaces and exact error strings.
- **Budget**: 250 lead calls per run in the profile, raised from 150 at the user's request. The pilot keeps 150, to compare with X2's SWE-agent runs.
- **SWE-bench Verified**: Harbor's verifier timeout scaled by 0.6, to the official harness's 1800 s. Images are Epoch AI's prebuilt equivalents of the official ones.
- **Qwen3-32B** keeps its native 32K window (no YaRN), non-thinking, with topic 16's append-only template. The other models are served at 128K with thinking on, at each vendor's agentic setting.
- **s15 benchmark profile**:
  - removed: teams, cron, worktrees and the mock MCP servers;
  - memory off;
  - permission policy: everything inside the task container is allowed, host-only tools are refused;
  - everything else is unchanged (loop, compaction, todo, subagent, skills).
- **Infrastructure failures are excluded and rerun**: cancelled trials, disk-guard kills and broken RPC.
- **Where task containers ran**:
  - Qwen3-32B's earlier TB trials, DeepSeek-V4-Flash and MiniMax-M2.7 ran on the shared host Docker daemon.
  - The Qwen phase (from 2026-10-12 18:45 UTC) ran in our own Docker-in-Docker daemon with its data on /data (`run/dind.md`), with the same images, resource limits and Harbor version.
  - The host daemon's root disk (~33 GB usable, shared) had limited how many SWE-bench / Pro images could be present at once. Before the switch, the disk guard killed 8 task containers to protect it, and free space dipped to 1.7 GB once (13:38 UTC).
  - Oracle checks passed in both setups. The nested daemon needed MTU 1460 on its networks; with 1500, a verifier's tool download stalled once during testing.
- **Qwen3-32B serving**:
  - In BF16 on one H100 it has 40.8K tokens of KV cache, about 1.25 full 32K contexts.
  - With four lanes on one GPU, median call latency rose from ~1.5 s to ~5 s until helper servers were added (`run/helper32.py`).
  - Agent timeouts (50 min on SWE-bench and Pro) were not reached because of this. On TB (15-60 min), some budget-bound runs became timeouts; both are failures, and Qwen3-32B is at the floor on TB.
- **Official cross-grade of the pilot**: 49 patches got a verdict from the official harness, all agreeing with Harbor. On 2 more patches the official harness produced no report (patch not applied); Harbor scored one of them unresolved and had no verdict for the other.

#### Setup and deviations (MiniMax-M2.7, phase e4: divergence-triggered full recomputation)

### EPIC on DeepSeek-V4-Flash (stage C: design and selftests only)

**Why a different design.** DeepSeek-V4-Flash has 43 layers. vLLM 0.31's model code, surveyed for this port, shows
three kinds of cached rows:
- **Sliding window.** Every layer keeps a 128-token window of its latent: 448 no-RoPE dims stored FP8, plus 64 RoPE
  dims stored bf16 and rotated at the token's position, GPT-J pairs.
- **Pooled entries.** 41 of the 43 layers also keep pooled entries: one per 4 tokens on C4 layers (overlapping
  windows) and one per 128 tokens on C128 layers. Each is a softmax-weighted sum of per-token compressor inputs plus
  a bias by offset in the window, rotated at the window start.
- **Indexer keys.** The 21 C4 layers also keep FP8 indexer keys, rotated before quantization. The indexer picks the
  top 512 pooled entries for each query.

These rows cannot be re-rotated in place:
- a shift that is not a multiple of the pooling ratio changes which tokens share a window and their offsets;
- indexer keys lose precision if rotated after quantization;
- the window keeps only 128 tokens, so there is nothing to copy back afterwards.

**Design B (`epic/epic_dsv4.py`).**
- **What is position-free.** Every cached quantity is computed by fused kernels from the current positions and from
  inputs that do not depend on position: the latent before RoPE, and the compressor and indexer inputs. All of
  these are functions of the layer's attention input, after the hyper-connection mix and the attention norm.
- **Store and substitute.** The connector keeps each computed token's attention input at every layer (43 × 4096 bf16
  per token, about 344 KB). At reused positions it substitutes the stored row through a forward pre-hook on
  `model.layers.i.attn`. The kernels then redo RoPE, FP8 quantization, pooling and the indexer keys at the new
  positions, which is shift's re-rotation done exactly.
- **Side effects.** Reused tokens' own queries and outputs change too. Their attention input is substituted again at
  every layer, so nothing from them reaches another position except through the substituted inputs.
- **The approximation.** Pooled windows that straddle an edit mix stale and fresh inputs.
- **Replication across ranks.** The latent and compressor GEMMs are replicated across tensor-parallel ranks, so every
  rank stores the same rows.
- **Locating rows.** The batch rows of planned positions come from the slot mapping of layer 0's sliding-window cache.
- **Server requirements.**
  - A connector that supports vLLM's hybrid memory allocator: DeepSeek-V4 has 5 KV cache groups, and without it
    vLLM would size every cache for every token.
  - `--enforce-eager`: vLLM captures CUDA graphs for DeepSeek-V4 even under compilation mode 0, and graphs skip the
    hooks.
  - No loads; the overshoot reserve is off.
  - No shadow probes: their K-row comparison needs per-head rows, which this cache does not have.
- **Compute saving.** None in this form: vLLM only serves prefix hits, so a reused token is still recomputed. A real
  implementation would skip the reused tokens' layers and rebuild only the cached quantities from the stored inputs.
  It would pay full price for any pooled window that straddles an edit.
