Telling the Agent What It Costs

A tool description says what a tool does and never what it costs. If the harness published its own measured latencies — or the hardware behind them — would the model route around the expensive tools?

model glm-5.3-flash (z.ai) stage 1 893 single-shot trials stage 2 80 multi-round runs stage 3 24 full s15 sessions

The answer depends entirely on whether the tools are substitutes

Asked in its original form — if read_file is advertised at 5 s, does the model still generate read_file tool_use? — the answer is yes, at exactly the same rate. But the same model, given two tools it is told are interchangeable, follows the advertised cost almost perfectly. Both facts come from the same prompts and the same afternoon.

Stage 1single-shot probes, 893 trials

Between substitutes, the cost decides — in any wording, from anywhere in the prompt

Two tools, read_via_alpha and read_via_beta, described as returning the same bytes for the same path. Unannotated, the model picks alpha 91% of the time; it is simply biased toward that name. Annotated, it picks alpha exactly 50% of the time — the rate counterbalancing produces when the choice is made purely on cost. The prior is not nudged, it is replaced.

The hardware wording never states a latency. It gives a working-set size and two bandwidths, and the model does the division: “Alpha is faster (HBM3 resident, 3.35 TB/s) vs beta (PCIe staging).” Where the information sits — tool description, system prompt, or both — makes no measurable difference, because information is not what is scarce.

Put the same numbers in a realistic pool and the model stops reading them

Probe C keeps the cost table and swaps the two twin channels for tools that answer different questions: read_file, grep, glob, bash and a recall_summary that returns a deliberately vague cached blurb. The question is a real one about a real file.

Pooled over all five read_file annotations: 45% of 160 trials against 44% of 32 unannotated trials. A sixty-second advertised latency on the tool the task obviously needs moves its selection rate by less than the spread between two samples of the same prompt.

The reasoning traces say why, and the contrast is total. In probe A the model mentioned the cost in 75–100% of trials. In probe C it mentions it in 0–3%. It does not weigh the cost and decide to pay it. It never raises the subject.

What closes the gap is an objective, not information

Probe D holds the pool, the question and the cost table fixed and adds one sentence of policy, and in the last cell a hard budget.

Stages 2 and 3real tool execution, then the real harness

Neither stage found room for the intervention to work

Stage 2 runs a real loop over repository files in a 2×2 design that separates an advertised 5-second cost from a really injected 5-second sleep. The enforce arm is the negative control: a model cannot perceive wall-clock time inside a request, so whatever separates it from the plain arm is noise.

On the value-lookup workload the lead answered with bash and a grep-shaped command in 12 runs out of 12, in every arm, and never called read_file once: the unannotated harness was already on the cheap route, so there was nothing to remove. On the comprehension workload it called read_file and pulled all 12.5 KB in 12 runs out of 12, in every arm — including the one told the call costs 5 s and instructed to prefer the cheapest tool that still works. That is correct: no set of grep matches answers “explain what this entry says”.

What follows

  1. Publishing a cost table is not a scheduling mechanism

    Real tool pools are pools of tools that do different things. read_file, grep and bash are not substitutes from the model's point of view: they answer different questions, and it picks on fit and stops.

  2. The information is cheap; the objective is what is scarce

    Annotating the real s15 pool costs 910 characters of tool definitions — about 230 tokens, 8.7 ms of prefill at the measured 0.038 ms per uncached token, and it sits in the stable prefix, so it is cached after the first call. The policy sentence costs 95 characters and is the part that moves behaviour.

  3. The intervention costs most when it is used, and on the output side

    When the model actually uses the annotation it narrates the comparison: replies grow from 53 to 71 output tokens for stated seconds, and to 84 when it has to divide the hardware numbers itself — 0.30 to 0.53 s of extra decode at the measured 17.4 ms per output token. When it ignores the annotation, reply length barely moves.

  4. Cost-aware routing stays in the harness — with one exception

    The tier-boundary costs this project has priced cannot be delegated to the model by writing them into the prompt. But model-side exposure does work between substitutable tiers, and a hot and a cold route to the same bytes is exactly that shape. If a tiered-memory prototype exposes both routes, it should publish ordered costs and state the objective alongside them.
