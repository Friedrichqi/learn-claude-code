# Related work: an autonomous, self-evolving harness that diagnoses serving bottlenecks and writes its own compensation tools

Background research, 2026-11-01, 05:05–06:10 UTC: 8 search agents over two rounds. A round-3 rerun at 16:40 UTC was meant to sweep the remaining venue lists for this topic too. It was stopped by the session's safety check before reaching them, so nothing in this note changed.

**Question (user).** Is there any paper on an autonomous, self-evolving harness system? The system would work like this:
- An **edge server** saves all agent traces, hardware and performance metrics, and congestion signals.
- It **calls other LLMs** to find the systematic root cause of a performance drop.
- It **writes compensation tool functions** and integrates them into the **cloud-level harness**.
- These functions guide the harness on how to approach, handle or work around the current bottleneck under load.

**Method.**
- **Round 1:** three parallel sweeps.
  - Diagnosis: autonomic computing and MAPE-K, LLM AIOps and root-cause analysis, LLM tuning from telemetry.
  - Synthesis: LLMs that write or evolve systems policies, plus self-driving-systems precedents.
  - Self-evolving agents and harnesses, tool creation, and harness–serving co-design under load.
- **Round 2:**
  - forward citations of the 16 closest papers;
  - all leads left over from round 1;
  - venue program sweeps: OSDI'26, NSDI'26, SOSP'25, MLSys'26, SIGCOMM'26, ML for Systems '25/'26, Resource-Aware Agentic AI '26, AgenticOS '26;
  - an arXiv sweep of Aug–Nov 2026;
  - a full-text re-check of the 5 closest papers.
- **Rows:** 600 for this topic in [`lit_review_1101_papers.csv`](lit_review_1101_papers.csv): 16 directly relevant, 159 building blocks, 425 background.
- **Verification:** every arXiv ID was re-resolved through the arXiv API and its title matched. Every DOI was matched through Crossref, and every other URL returned HTTP 200. No row in this topic is unverified.
- **Query log:** [`lit_review_1101_search_log.md`](lit_review_1101_search_log.md).
- **Saturation:** reached on the question of whether anyone has built the full loop.
- **Still unread:** the EuroSys'26 and ATC'26 lists (pages unavailable), the NeurIPS'26 AgenticOS workshop papers (OpenReview blocked), and the full ICLR'26, ICML'26 and NeurIPS'25 main-track lists.

**Short answer: no paper builds this loop end to end. Three separate lines each build about half of it, and none joins them:**

| line | what it closes | what it lacks |
|---|---|---|
| **(A) An LLM rewrites serving policy from live telemetry** (Autopoiesis, SEIS, AgentServeSim, VibeServe; SchedCP for the OS) | telemetry → LLM → code → hot deploy → repeat | the code goes into the *serving engine*, not the harness; no explicit root-cause step; agent traces are not used |
| **(B) Self-evolving harnesses** (Agentic Harness Engineering, HarnessFix, Meta-Harness, Self-Harness, HarnessPro, OpsHarness) | traces → LLM root-cause report → new tools, middleware and prompts *in the harness* → repeat | they optimise task success and tokens offline; none reads serving load, KV or congestion signals |
| **(C) Harnesses that act on serving load** (CONCUR, INFRAMIND, HEAR, Decoupling Readiness from Release) | live vLLM/SGLang queue and KV signals → harness holds, admits or re-plans agent calls | the policy is hand-written or trained offline; nothing is diagnosed or generated by an LLM |

The user's idea is the composition: **(B)'s diagnosis-to-harness-code loop, fed by (C)'s serving signals, running online the way (A) does.** No paper builds it. The edge/cloud split is also new. The only edge → central-LLM → code-back loop found is in Wi-Fi rate control (IteRate). There the direction is the reverse of the user's: devices stream telemetry *to* a central LLM.

Six independent papers back the user's own finding that models ignore advisory efficiency signals (§5). That finding is the strongest motivation for making the generated compensation *enforced harness code*, not guidance text for the model.

## 1. The target loop, split into parts

| # | part | what counts as "covered" |
|---|---|---|
| S1 | **Telemetry store** | agent traces + HW/perf metrics + congestion signals (queue, KV usage, preemptions), collected automatically |
| S2 | **LLM root-cause analysis** | an LLM explains the *systematic* cause of a performance drop, not just a single failure |
| S3 | **Synthesis** | the LLM writes new code, tools or policies, not just parameter values |
| S4 | **Harness deployment** | the artifact becomes part of the agent harness or the agents' toolset |
| S5 | **Online, under load** | it acts while the system runs under live load, not in an offline benchmark loop |
| S6 | **Closed loop** | re-measurement decides whether the artifact is kept, and the cycle repeats automatically |
| + | **Edge/cloud split** | diagnosis runs off the critical path (edge), guidance runs in the cloud harness |

## 3. The literature in five groups

### 3.1 Autonomic computing and self-adaptive systems: the classic frame

The user's loop is a **MAPE-K loop** (Monitor, Analyze, Plan, Execute over shared Knowledge) with LLMs in the Analyze and Plan steps. It also generates new Execute-step *effectors*, which classic MAPE-K never did.
- **Foundations:**
  - Kephart & Chess, "The Vision of Autonomic Computing" ([IEEE Computer 2003](https://doi.org/10.1109/MC.2003.1160055));
  - Rainbow, architecture-based self-adaptation ([2004](https://doi.org/10.1109/MC.2004.175)).
- **LLMs in the loop:**
  - "Can LLMs make it a reality?" ([2407.14402](https://arxiv.org/abs/2407.14402)), a multi-agent MAPE-K over microservices;
  - "Reimagining Self-Adaptation" ([ICSA-C'24](https://arxiv.org/abs/2404.09866));
  - the GenAI-for-self-adaptive-systems roadmap ([TAAS](https://arxiv.org/abs/2512.04680));
  - SelfEvolve ([SEAMS'26](https://arxiv.org/abs/2604.16314)), runtime code generation for software self-extension;
  - CALM ([SEAMS'26](https://arxiv.org/abs/2602.03632)), MAPE-K for QoS-aware routing across small LMs;
  - self-healing agentic orchestrators ([2606.01416](https://arxiv.org/abs/2606.01416)).
- **What they lack:** none targets LLM-serving congestion or deploys into an agent harness. The SEAMS line is the right vocabulary for the paper (knowledge base = the edge trace store; effectors = the compensation tools).

### 3.2 LLM root-cause analysis: the edge server's "Analyze" step

- **Cloud incident RCA:**
  - Recommending root causes and mitigations ([ICSE'23](https://arxiv.org/abs/2301.03797));
  - RCACopilot ([EuroSys'24](https://arxiv.org/abs/2305.15778));
  - RCAgent ([CIKM'24](https://arxiv.org/abs/2310.16340));
  - LLM agents for RCA ([FSE'24](https://arxiv.org/abs/2403.04123));
  - STRATUS ([NeurIPS'25](https://arxiv.org/abs/2506.02009));
  - Diviner ([2610.21281](https://arxiv.org/abs/2610.21281));
  - D-Bot ([VLDB'24](https://arxiv.org/abs/2312.01454)) and Panda ([CIDR'24](https://vldb.org/cidrdb/2024/panda-performance-debugging-for-databases-using-llm-agents.html)) for databases.
- **Benchmarks:** OpenRCA ([ICLR'25](https://iclr.cc/virtual/2025/poster/32093)), AIOpsLab ([MLSys'25](https://arxiv.org/abs/2501.06706)), ITBench, SRE-Marathon, and others in the CSV.
- **RCA for LLM serving and GPU clusters**, closest to the user's edge analyzer:
  - TELLER ([ASE'26](https://arxiv.org/abs/2608.01975)), non-intrusive cross-layer RCA for LLM inference;
  - StriaTrace ([OSDI'26](https://www.usenix.org/conference/osdi26/presentation/wu-haonan)), tracing and diagnosis for online LLM inference;
  - Kunlun Anomaly Troubleshooter ([2511.05978](https://arxiv.org/abs/2511.05978));
  - "Beyond Microservices" ([2603.02057](https://arxiv.org/abs/2603.02057)), which finds that web-scale RCA methods transfer poorly to GPU-driven LLM workloads;
  - XPerf ([2608.20370](https://arxiv.org/abs/2608.20370)), agentic serving benchmarks;
  - ASAP ([2511.03844](https://arxiv.org/abs/2511.03844)) and Argus ([2609.35508](https://arxiv.org/abs/2609.35508)), agentic bottleneck localisation for LLM training and system software;
  - PROMPTS (Google, [MLSys'26](https://research.google/pubs/prompts-performance-optimization-via-multi-agent-planning-for-llm-training-and-serving/)), where an Analyzer agent diagnoses profiler data and proposes sharding configs.
- **RCA that improves itself:**
  - OpsHarness ([2608.25661](https://arxiv.org/abs/2608.25661)), a self-evolving harness *for* RCA;
  - SDO ([2610.14547](https://arxiv.org/abs/2610.14547)), where incidents become playbooks plus detector scripts, and cheap detectors call the LLM only when they fire;
  - GraphMind ([2605.17617](https://arxiv.org/abs/2605.17617)) and Progressive Crystallization ([2607.07052](https://arxiv.org/abs/2607.07052)), which turn agent exploration into deterministic workflows.
- **What they lack:** they diagnose failures and incidents, mostly reliability rather than load. The output goes to an operator or to the RCA agent's own harness, never to the *workload* agents' harness.

### 3.3 LLMs that write systems policies: the "Plan" and synthesis step

- **Evolutionary code search:**
  - FunSearch ([Nature'23](https://www.nature.com/articles/s41586-023-06924-6));
  - EoH ([ICML'24](https://arxiv.org/abs/2401.02051));
  - ReEvo ([NeurIPS'24](https://arxiv.org/abs/2402.01145));
  - AlphaEvolve ([2506.13131](https://arxiv.org/abs/2506.13131)), which evolved a Borg scheduling heuristic deployed at Google;
  - OpenEvolve ([GitHub](https://github.com/codelion/openevolve)).
- **Systems-research framing:**
  - "Barbarians at the Gate" (ADRS, [2510.06189](https://arxiv.org/abs/2510.06189)) and "Let the Barbarians In" ([2512.14806](https://arxiv.org/abs/2512.14806)): evolved MoE placement, scheduling and SQL policies, all evaluated in simulators;
  - "Man-Made Heuristics Are Dead" ([HotNets'25](https://arxiv.org/abs/2510.08803));
  - Glia ([2510.27176](https://arxiv.org/abs/2510.27176)): routing, scheduling and autoscaling for an LLM-inference cluster at human-expert level, at design time;
  - Vulcan ([EuroSys'27](https://arxiv.org/abs/2512.25065));
  - AtumAI ([2608.02569](https://arxiv.org/abs/2608.02569));
  - HELIOS ([2609.09164](https://arxiv.org/abs/2609.09164)), guardrailed LLM evolution of orchestration policies;
  - TRACE ([2610.01887](https://arxiv.org/abs/2610.01887)): a Reasoner mines system logs for hidden dynamics, and a Coder writes surrogate *tools* that the evolved heuristics call. This is the closest analogue of "diagnosis produces tools".
- **Into the LLM-serving engine:**
  - **Autopoiesis** ([2604.07144](https://arxiv.org/abs/2604.07144)): an online loop that rewrites the serving engine's scheduling code from a sliding window of live dynamics and hot-swaps it;
  - SEIS ([2610.04646](https://arxiv.org/abs/2610.04646)): agentic self-evolution of a whole mini-sglang engine, offline;
  - VibeServe ([ICML'26](https://arxiv.org/abs/2605.06068));
  - AgentServeSim ([2606.09613](https://arxiv.org/abs/2606.09613)): OpenEvolve over agent-serving KV-retention and scheduling policies, gaining only 0.5–2.8% over hand-written seeds;
  - LLM-evolved KV eviction policies ([2608.14555](https://arxiv.org/abs/2608.14555));
  - FlashInfer-Bench ([MLSys'26](https://arxiv.org/abs/2601.00227)): LLM-generated kernels, benchmarked on serving traces, hot-substituted into SGLang/vLLM.
- **Into the OS, live:**
  - SchedCP ([2509.01245](https://arxiv.org/abs/2509.01245)): Claude-Code subagents profile workloads, write sched_ext eBPF schedulers, verify them, then canary-deploy;
  - AKTS ([2609.12276](https://arxiv.org/abs/2609.12276)): sub-microsecond policy switching for agents;
  - "Expert in Residence" ([NeurIPS'25 workshop](https://neurips.cc/virtual/2025/129122)): always-on OS tuning;
  - ECO ([2503.15669](https://arxiv.org/abs/2503.15669)): Google's fleet-profile-driven LLM code rewrites;
  - Meta's capacity-efficiency agents ([blog](https://engineering.fb.com/2026/04/16/developer-tools/capacity-efficiency-at-meta-how-unified-ai-agents-optimize-performance-at-hyperscale/)): regression detection → root-cause PR → fix-forward PR.
- **Fast path / slow path**, the architecture the user describes:
  - VibeWAF ([AgenticOS'26](https://os-for-agent.github.io/papers/AgenticOS_2026_paper_24.pdf)): a fast rule engine serves traffic while an LLM analyses misses and writes new rules;
  - IteRate ([2605.02542](https://arxiv.org/abs/2605.02542)): devices stream telemetry to a central LLM that writes eBPF rate control and pushes it back over the air — the only edge/central split found.
- **What they lack:** the target is the engine, the kernel, a scheduler or a rule base, never the agent harness. Most are evaluated in a simulator. Re-checks found that Autopoiesis's headline 53%/34% gains are trace completion times under its execution model, and that SchedCP's canary and auto-revert is designed but not evaluated.

### 3.4 Self-evolving harnesses and tool making: the "deploy into the harness" step

- **Harness evolution from traces:**
  - **AHE** ([2604.25850](https://arxiv.org/abs/2604.25850)): an Agent Debugger distils trajectories into root-cause reports, and an Evolve Agent edits prompts, tool code, middleware, skills, sub-agents and memory. Every edit carries a falsifiable prediction checked in the next round.
  - HarnessFix ([2606.06324](https://arxiv.org/abs/2606.06324)): a trace IR plus per-layer flaw attribution and scoped repairs.
  - Meta-Harness ([2603.28052](https://arxiv.org/abs/2603.28052)), Self-Harness ([2606.09498](https://arxiv.org/abs/2606.09498)), HarnessPro ([2610.26770](https://arxiv.org/abs/2610.26770)), Harmony Harness ([2610.15150](https://arxiv.org/abs/2610.15150)), MoMHa ([NeurIPS'26](https://arxiv.org/abs/2609.30967)).
  - Efficiency-oriented ones, which optimise *tokens or model cost*, not server load: HarnessMM ([2610.32813](https://arxiv.org/abs/2610.32813)) and "Better Harnesses, Smaller Models" ([2607.08938](https://arxiv.org/abs/2607.08938)).
  - An empirical study of how harnesses self-evolve ([2610.34938](https://arxiv.org/abs/2610.34938)).
  - About 150 further 2026 harness-evolution papers that optimise accuracy only were checked by title. One representative is kept in the CSV.
- **Tool making:**
  - LATM ([ICLR'24](https://arxiv.org/abs/2305.17126)), Voyager ([2305.16291](https://arxiv.org/abs/2305.16291)), Live-SWE-agent ([2511.13646](https://arxiv.org/abs/2511.13646)), which creates tools at runtime, and SkillCache ([NeurIPS'26 workshop](https://neurips.cc/virtual/2026/170691)), which compiles skill traces into fast-path capsules inside the Claude Code harness;
  - **Tool-Making in Low-Latency Systems** ([EMNLP'26 industry](https://arxiv.org/abs/2607.08010)): a production alarm-triage agent whose tool-maker compiles repeated SOP steps into versioned tools (−42% p50 latency). The latency here is the agent's own code generation, not server load.
- **Self-improving agents:** Darwin Gödel Machine ([2505.22954](https://arxiv.org/abs/2505.22954)), SICA ([2504.15228](https://arxiv.org/abs/2504.15228)), ADAS ([ICLR'25](https://arxiv.org/abs/2408.08435)), AFlow ([ICLR'25](https://arxiv.org/abs/2410.10762)).
- **Context and playbook evolution:** ACE ([ICLR'26](https://arxiv.org/abs/2510.04618)) and GEPA ([ICLR'26](https://arxiv.org/abs/2507.19457)).
- **Surveys:** [2507.21046](https://arxiv.org/abs/2507.21046) and [2508.07407](https://arxiv.org/abs/2508.07407).
- **Infrastructure:** **Reef** ([GitHub](https://github.com/Human-Agent-Society/Reef)) is an inference proxy over vLLM/SGLang. It records every interaction and evolves and publishes the harness (GEPA, Meta-Harness recipes) from *task-quality* feedback. It has the user's "edge store sits next to the server" shape, but uses no load signals and has no root-cause step.
- **What they lack:** the objective is task success, tokens or cost. No paper feeds serving-side congestion (KV usage, queue depth, preemptions) into harness evolution.

### 3.5 Harness ↔ serving signals under load: the "guide the harness through the bottleneck" step

- **Hand-written or trained harness-side controllers that read engine load:**
  - **CONCUR** ([2601.22705](https://arxiv.org/abs/2601.22705)): an AIMD agent-admission window driven by KV usage and cache hit rate, up to 4.09×.
  - **Decoupling Readiness from Release** ([2609.10964](https://arxiv.org/abs/2609.10964)): holds ready turns under a congestion-shrunk budget, 2.06–3.50× lower P95 workflow time.
  - **INFRAMIND** ([2606.11440](https://arxiv.org/abs/2606.11440)): a CMDP-trained policy picks model, reasoning depth and the agent's reasoning prompt from vLLM `/metrics` before every call.
  - **HEAR** ([2610.06597](https://arxiv.org/abs/2610.06597)): a bidirectional harness–engine protocol in which the engine returns KV residency, queue state and pressure.
  - A policy-driven runtime layer ([2605.27744](https://arxiv.org/abs/2605.27744)).
  - "Ask the Tool, Don't Guess" ([2609.18849](https://arxiv.org/abs/2609.18849)).
  - AgentRM ([2603.13110](https://arxiv.org/abs/2603.13110)).
  - Patient Bytes ([AgenticOS'26](https://os-for-agent.github.io/papers/AgenticOS_SOSP_2026_paper_26.pdf)).
  - Memory-augmented backpressure ([2608.00914](https://arxiv.org/abs/2608.00914)).
  - Cognitive Friction ([2603.30031](https://arxiv.org/abs/2603.30031)): agents price tool queries by network load.
- **Engine-side agent awareness** (background):
  - Autellix ([2502.13965](https://arxiv.org/abs/2502.13965)), Parrot ([OSDI'24](https://arxiv.org/abs/2405.19888)), Continuum ([2511.02230](https://arxiv.org/abs/2511.02230)), Coda ([2610.03088](https://arxiv.org/abs/2610.03088)), ThunderAgent ([2602.13692](https://arxiv.org/abs/2602.13692)), KVTether ([2609.39819](https://arxiv.org/abs/2609.39819)), keepalive economics ([2607.19214](https://arxiv.org/abs/2607.19214)), Sutradhara ([2601.12967](https://arxiv.org/abs/2601.12967)), Murakkab ([OSDI'26](https://arxiv.org/abs/2508.18298)), Nalar ([2601.05109](https://arxiv.org/abs/2601.05109)), software-defined agentic serving ([2601.03197](https://arxiv.org/abs/2601.03197)).
  - Workload characterisation: TraceLab ([2606.30560](https://arxiv.org/abs/2606.30560)) and Copilot traces ([2608.00101](https://arxiv.org/abs/2608.00101)).
- **What they lack:** every policy here is designed by people or trained offline, then frozen. When the bottleneck moves (KV capacity, prefill interference, tool-time stragglers), nobody rediagnoses it or writes a new policy.

## 4. The five closest works and exactly what each misses

1. **Autopoiesis** ([2604.07144](https://arxiv.org/abs/2604.07144)).
   - Has: the closest *online* loop. The data plane snapshots a sliding window of arrivals and cluster state. An asynchronous control plane runs LLM program synthesis that rewrites `should_reschedule`/`schedule`, scores candidates by trace replay with cost-breakdown feedback, and hot-deploys the winner.
   - Misses:
     - **S4:** the code goes into the serving engine's scheduler, not the harness, and agents never see it;
     - **S2:** no explicit root-cause step — feedback is a cost breakdown, not a diagnosis;
     - **S1 for agents:** no agent traces and no agent-level signals;
     - **evidence:** headline gains come from the paper's execution model, not stated as GPU measurements.
2. **Agentic Harness Engineering** ([2604.25850](https://arxiv.org/abs/2604.25850)).
   - Has: the closest *harness* loop. Raw trajectories become drill-down evidence, an LLM writes root-cause reports, and new tool and middleware code is committed to the harness, with falsifiable predictions per edit.
   - Misses:
     - **S1 for load:** no system, KV or congestion telemetry;
     - **objective:** Pass@1 only;
     - **S5:** offline rounds over a benchmark;
     - **topology:** no edge/cloud split.
3. **INFRAMIND** ([2606.11440](https://arxiv.org/abs/2606.11440)), with CONCUR and Decoupling Readiness from Release.
   - Has: the harness reads live vLLM queue and KV signals before every call and changes what agents do. INFRAMIND even chooses the agent's reasoning prompt from telemetry.
   - Misses:
     - **S2/S3:** the policy is an RL-trained network (INFRAMIND) or hand-designed (CONCUR, Decoupling), with no LLM diagnosis and no generated tools;
     - **adaptation:** frozen after training.
4. **Self-Defining Operator** ([2610.14547](https://arxiv.org/abs/2610.14547)).
   - Has: the best *architecture* match. Generated non-LLM detectors watch telemetry continuously and call the LLM only when one fires; each resolved incident becomes playbooks plus new detector scripts. This is the cheap-edge-monitor, expensive-LLM-on-trigger split.
   - Misses:
     - **fault class:** crash loops and config faults, not load or congestion;
     - **S4:** the artifacts serve the operator agent's own harness, not the workload agents;
     - **domain:** not LLM serving.
5. **SchedCP** ([2509.01245](https://arxiv.org/abs/2509.01245)).
   - Has: the most complete *deploy-safely* loop. perf/eBPF profiling → LLM agents → generated eBPF schedulers → verifier → live deployment → a policy repository that keeps evolving.
   - Misses:
     - **target:** the Linux scheduler, not the harness and not LLM serving;
     - **evidence:** canary deploy and revert are not evaluated.

**Runners-up:**
- **HEAR**: the signal channel the generated tools would use, with hand-written policies.
- **IteRate**: the only edge/central split, in the Wi-Fi domain.
- **TRACE**: logs → hypotheses → surrogate tools for evolved heuristics, evaluated offline.
- **Tool-Making in Low-Latency Systems**: production tool synthesis into an agent harness, for the agent's own latency.
- **Reef**: an inference-proxy trace store that evolves the harness from quality feedback.
- **Glia**: LLM-designed serving-cluster policies at design time.

## 5. Evidence that "guidance" must be enforced code, not advice to the model

Our topics 18–19 found the following:
- Agents ignored model-callable wait tools and efficiency signals. MiniMax-M2.7 in topic 19 made 3 waits in 21k calls, and 1 in 3.6k at N = 64/128.
- Harness-side gates and twins gave 1.4–2.8×.

Independent work published in 2026 reports the same pattern:

| work | finding |
|---|---|
| **Will the Agent Recuse?** ([2606.06460](https://arxiv.org/abs/2606.06460)) | when a server sent *throttle* signals, agents showed no measurable self-limiting; enforcement had to come from the harness |
| **SysContract** ([NeurIPS'26 ML for Systems workshop](https://neurips.cc/virtual/2026/179019)) | LLM agents controlling serving stacks with invariants written into the prompt kept serving within its TTFT and KV limits only 40 % of the time; a machine-checked admit/rollback/stop runtime was needed |
| **AOS-Bench** ([2610.33178](https://arxiv.org/abs/2610.33178)) | a fixed concurrency of 2 comes within 4 points of the best policy the agent manages itself |
| **On the Clock** ([2610.10833](https://arxiv.org/abs/2610.10833)) | agents fail to turn a budget stated in the prompt into controlled use of time; timing feedback from the harness is needed |
| **Same Pieces, Different Servers** ([2603.02348](https://arxiv.org/abs/2603.02348)) | an agent's own long requests slow its short decisions more than tenfold, and a simple client-side admission rule cuts that slowdown by 59 % |
| **From Agent Failures to Text Policies** ([2607.20668](https://arxiv.org/abs/2607.20668)) | guidance text generated from trajectories does not reliably beat fixed prompting |

**Implication for the design:** the "compensation tools" should be generated *harness middleware*, such as admission gates, hold/resume rules, re-plan triggers and context trimming under KV pressure. They run without the model choosing to call them. Text hints for the model come second.

## 6. Gap statement and the questions a paper would have to answer

**Gap.** Nobody has closed the loop from serving-side bottleneck evidence, through LLM diagnosis, to generated and enforced harness code that is re-measured online. Line (B) shows LLMs can write harness code from traces. Line (C) shows harness-side load control pays 1.4–4×. Line (A) shows online LLM policy synthesis is feasible for the engine.

**Questions, each tied to a weakness of the closest work:**
1. **What evidence goes into diagnosis.**
   - AHE needed "experience observability" to make millions of trajectory tokens usable. A serving-aware version must join agent traces with engine metrics (KV usage, preemptions, queue, prefill/decode interference) on one timeline.
   - "Observability Debt" ([NeurIPS'26 workshop](https://neurips.cc/virtual/2026/170685)) argues that this joined record does not exist today.
   - TELLER and StriaTrace show how to get cross-layer causes for LLM inference.
2. **What the generated artifact is.**
   - Middleware, gates and policies (the CONCUR/Decoupling style), not prompts (§5).
   - Each needs a typed interface to HEAR-like engine signals so it can be verified.
3. **How to evaluate before deploying.**
   - Autopoiesis and AgentServeSim use trace-replay simulators, and AgentServeSim's gains are small (0.5–2.8%). AgentTwin ([NeurIPS'26 workshop](https://neurips.cc/virtual/2026/179024)) synthesises executable abstractions of production systems for this purpose.
   - Our replay harness from topic 21 is a candidate fitness function.
4. **Safety under live load.**
   - SchedCP (verifier plus canary), SysContract (stop–check–act), AKTS (fast policy switching), HELIOS (guardrails) and AIChilles ([2606.15834](https://arxiv.org/abs/2606.15834), hidden weaknesses in AI-evolved systems) give the toolkit.
   - None has been applied to harness code.
5. **Noisy fitness.** Agent runs are high-variance. "Survival of the Luckiest" (2026, cited by ADRS follow-ups; no arXiv copy found) warns that noisy evaluation misleads agentic evolution. The loop needs repeated or paired measurements, which matches our practice of paired conditions in topics 18–21.
6. **Edge/cloud split.**
   - SDO's cheap-detector, LLM-on-trigger pattern and VibeWAF's fast/slow path fit the split: the edge runs detectors and the LLM, the cloud harness runs the compiled tools.
   - IteRate is the only measured edge/central loop. It sends telemetry inward and code outward, the reverse orientation of the user's design.
   - "The World Won't Wait" ([2610.20665](https://arxiv.org/abs/2610.20665)) splits the work across two timescales: a slow teacher studies failures offline and adopts written corrections only if validation improves, while the fast student acts in real time without calling the teacher. Its objective is task progress, not serving load.
7. **When to evolve.** The trigger can be drift detection (SDO detectors) or a fixed cadence (Autopoiesis's sliding window). Moving bottlenecks, for example from KV capacity to prefill interference, are exactly the topic 13 and topic 20 findings.
