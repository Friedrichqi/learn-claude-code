Reusing the KV cache when the prefix changes

A transformer keeps the keys and values it computed for every token. Serving engines reuse them only when a new prompt starts with exactly the same tokens. 21 · Background · what a language model does

A decoder-only transformer reads the prompt once, then writes one token at a time, feeding each new token back in

Generation is a loop of forward passes

  • Token: a word piece. Qwen3 knows 151,936 of them; each pass outputs one probability for each.
  • Prefill: the whole prompt goes through the model in one pass, many tokens at once.
  • Decode: one pass per new token; each pass reads what was kept for all earlier tokens.
  • Each pass runs the token(s) through a stack of identical blocks (right): attention mixes information between tokens, the MLP transforms each token on its own, and the residual path carries each token's running representation from block to block.

Sources: Vaswani et al., Attention Is All You Need, NeurIPS 2017; Qwen Team, Qwen3 Technical Report, arXiv 2505.09388. Sizes from Qwen/Qwen3-8B/config.json. Drawn as the plain block: Qwen3 keeps only 8 key/value heads for its 32 query heads and normalizes q and k per head before RoPE.

31 · Background · attention and the KV cache

Attention is a soft lookup over earlier tokens' keys and values; keeping them (the KV cache) makes each new token cost one step

Real weights: Qwen3-8B, first layer

Only in the first layer are these rows and columns the words themselves. From the second layer on, each position holds a hidden state that has already mixed in the tokens before it, so it is no longer just the word. That is why reused KV carries its old context (slide 6).

A soft database lookup

The names come from databases: a query looks for the entry whose key matches and returns its value. Attention does this softly: token i's query is compared with every earlier token's key, and token i receives a weighted sum of all their values, with more weight where the key matches the query better.

qi = xiWq    kj = xjWk    vj = xjWv   x: a row vector
outi = Σj ≤ i softmaxj( qikj⊤ / √dhead ) · vj

Causal attention gives the KV cache

Token i attends only to tokens 1…i. If we store the keys and values of tokens 1…i−1 (the KV cache), producing token i needs only its own q, k and v, and the first i−1 tokens never have to be prefilled again.

Question: why is there no Q cache?

A past token's query was used once, to compute that token's own output, and that output is done. A new token compares its own query with the past keys and reads the past values, so only K and V are needed later.

Generating three tokens

bytes/token = 2·L·Hkv·dhead·2
Qwen3-8B:  2·36·8·128·2 = 144 KiB
Qwen3-32B: 2·64·8·128·2 = 256 KiB

L = layers; Hkv = key/value heads, 8 per layer in Qwen3; the first 2 counts K and V, the last is 2 bytes per bf16 number. A 9,054-token prompt, the average in our experiment, holds 1.24 GiB of KV on Qwen3-8B and 2.21 GiB on Qwen3-32B.

41 · Background · positions

RoPE stores position as a rotation, so a cached key can be moved to a new position by rotating it again

One pair of a key, at two positions

Attention alone ignores word order. Rotary position embedding (RoPE) adds it by turning each query and key by an angle that grows with the token's position. Rm is that rotation for position m; as in slide 3, vectors are rows and matrices act on the right.

query at position m:  qm = (xmWq) Rm     key at position n:  kn = (xnWk) Rn
attention sees:  qmkn⊤ = (xmWq) Rm−n (xnWk)⊤   only the distance m − n
move a cached key:  kn+δ = kn Rδ   one more rotation; pair i turns by angle θi per position, θi = (106)−2i/128
  • A 128-number key is 64 pairs, and each pair turns like a clock hand. Pair 0 turns 1 radian per token and separates neighbours; pair 63 turns about a millionth of a radian and tracks long distances.
  • RoPE rotates only queries and keys. We only care how far apart two tokens are, and q·k⊤ sees exactly that. Values are what a token passes on; rotating them too would stamp an absolute position into every token's output.
  • So a key computed at position n can be moved to n + δ by one more rotation, and nothing is recomputed. Our experiments call this shift RoPE.

The rotation fixes the position part of a cached key exactly. Slide 6 shows what it cannot fix.

Sources: Su et al., RoFormer: Enhanced Transformer with Rotary Position Embedding, arXiv 2104.09864 (Neurocomputing 2024). Qwen3 uses rope_theta = 1,000,000 and head_dim 128 (config.json). With rows and right-multiplication, RmRn⊤ = Rm−n and RnRδ = Rn+δ.

62 · Why gluing cached pieces breaks

Two separately prefilled sentences do not glue into one: B's cache never saw A, and above layer 0 its old position is baked in

Reason 1 · B never attends to A · real weights, Qwen3-8B, layer 3

Reason 2 · RoPE can be fixed only at layer 0

  • Layer 0: a key is the token's embedding times Wk, rotated by its position. Re-rotating by δ gives exactly the key a joint prefill computes: the measured largest relative error is 5.5×10−4, against 0.094 without the rotation.
  • Layers 1 to n−1: keys and values come out of nonlinear layers (attention, MLP) that ran with B at its old positions. B's first token, for instance, was computed as the start of a sequence. That old position is now baked into the hidden state, and rotating the cached key cannot take it out.

A full prefill is the ground truth. The papers ask which few tokens to re-prefill.

7Paper · CacheBlend, EuroSys 2025 · the few tokens that deviate

CacheBlend re-prefills the ~15% of tokens whose cached KV deviates most, restoring attention across reused chunks

TTFT
2.2–3.3× lower than full recompute; throughput 2.8–5× higher
quality
within 0.01–0.03 F1 / ROUGE-L of full recompute; 0.1–0.2 F1 above full KV reuse
setup
Mistral-7B, Yi-34B, Llama-70B; 2WikiMQA, MuSiQue, SAMSum, MultiNews

Problem

RAG prompts glue several retrieved chunks before a question. Prefix caching reuses only the first chunk. Reusing each chunk's own precomputed KV drops the chunks' attention to each other, and the answer goes wrong (Figure 3).

Key observations

  • Attention is sparse: a few tokens carry most of the importance in the prompt, so only a few need fixing.
  • A token that deviates most at one layer tends to deviate most at the next, so re-prefilling one early layer can pick them.

Method

  • Rotate every reused key to its new position.
  • First layer: re-prefill every token, compare with the cached KV, keep the top ~15% (high-KV-deviation, "HKVD" tokens). Later layers: re-prefill only those, narrowing the set gradually.
  • Re-prefill layer i while layer i+1's KV loads from CPU or SSD: 15% takes about 3 ms per layer against 16 ms to load it from NVMe, so the work hides behind the load.

In our experiment

CacheBlend 5% and 15% follow LMCache's version: layer 0 in full, then only the moved tokens whose layer-1 key deviates most. Both restore Qwen3-32B's SEARCH/REPLACE copies (74.5% and 72.6%, against 61.1% for shift RoPE and 72.6% for full prefill) but close only 45–66% of Qwen3-8B's "gone" gap (slides 12–14).

Source: Yao, Li, Liu, Ray, Cheng, Zhang, Du, Lu, Jiang. CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion. EuroSys 2025 (arXiv 2405.16444); figure reproduced from arXiv v3; numbers as the paper reports them. Implemented in LMCache (lmcache/v1/compute/blend/blender.py). 8Paper · EPIC, ICML 2025 · the first tokens of each chunk

EPIC re-prefills only the first few tokens of each reused chunk, because those tokens become attention sinks

TTFT
up to 8× lower, throughput up to 7× higher than existing systems; up to 3× faster TTFT than CacheBlend on a single request
accuracy
within 7% of CacheBlend's, already with k = 2 (LegoLink-2)
setup
Mistral 7B, Llama 3.1 8B, Yi Coder 9B; 2WikiMQA, MuSiQue, HotpotQA, SAMSum, MultiNews

Problem

The same as CacheBlend's: chunks cached separately, each starting at position 0, then glued before a question (RAG, few-shot prompts).

Key observation: attention sinks

An LLM gives disproportionately large attention to the first tokens of a sequence: every later token can see them during token-by-token decoding, so the model learns to park spare attention there. A chunk cached alone starts with such tokens, so after gluing every chunk start is a fake sink that pulls attention away from the content (the bright columns in Figure 4). Our Qwen3-8B example on slide 6 shows it: B's first token takes 25–94% of B's attention when B is prefilled alone, 1–11% after A.

LegoLink

  • If each chunk's first few tokens draw most of the attention, why not re-prefill just those? LegoLink re-prefills the first k tokens of every chunk except the first (k ≤ 32 in their runs), so they see the real context.
  • The set is fixed in advance, with no deviation pass: cost O(kN), growing with the number of chunks, against CacheBlend's full first layer, O(N²). CacheBlend's selection takes 16.3–63.56% of its TTFT.

In our experiment

EPIC 32 and EPIC 128 re-prefill the first 32 or 128 tokens of each moved block (4.4% and 10.8% of the moved tokens). EPIC 32 restores 32B's copies (72.0%); EPIC 128 brings 8B's "gone" answers back to 55.3% (full prefill 57.5%).

Source: Hu, Huang, Wang, Wang, Hu, Zhang, Feng, Chen, Shan, Xie. EPIC: Efficient Position-Independent Caching for Serving Large Language Models. ICML 2025, PMLR 267:24391–24402 (arXiv 2410.15332); Figure 4 rendered from arXiv v3 page 5; numbers as the paper reports them. Attention sinks: Xiao et al., ICLR 2024. Our arms: README §B2.1, §B3.

9Paper · KVLink, NeurIPS 2025 · trained link tokens

KVLink appends five trained link tokens to each cached document; they carry no meaning and exist only to read the documents before them

accuracy
+4% average QA accuracy over prior methods across 7 datasets; Llama-3.2-1B on Natural Questions: 45.0 vs Block-Attention 39.0 vs CacheBlend 25.7
TTFT
−96% against standard prefill at a 5,000-token context

Problem

The same as CacheBlend's and EPIC's: documents cached one by one, then glued before a question.

Key observation (the storyline)

EPIC re-prefills each chunk's first tokens because they soak up attention. But those tokens are still real words with their own meaning: re-prefilled, they mostly reconnect to the words related to them, not to everything that came before. So why not add tokens that mean nothing and are trained for one job, reading every earlier token and carrying the documents' combined meaning forward?

Method

  • Link tokens: after each document, K = 5 trainable special tokens with no meaning of their own. They are computed at inference and attend to all earlier documents (and their link tokens) plus their own document.
  • Document tokens keep attending only within their document, so each document's KV can be cached once, alone.
  • Positions: each document's KV is stored without rotation and rotated to its place in the full sequence at inference.
  • Fine-tuning: full fine-tuning for 6,000 steps (batch 64, 8×H100) on 2WikiMQA, TriviaQA, FineWeb text and Tülu 3, so the model learns to use the link tokens and keeps its general skills. Models: Llama-3.2-1B and 3B, Llama-3.1-8B (instruct).

Trade-off

Almost nothing is re-prefilled per request, but the model's weights change. A server that must run an unmodified model cannot use it, so our experiment does not test it.

Source: Yang, Hou, Wei, Bao, Chang. KVLink: Accelerating Large Language Models via Efficient KV Cache Reuse. NeurIPS 2025 (arXiv 2502.16002v4); figure reproduced from arXiv v4; numbers as the paper reports them. The storyline is our reading; the paper presents link tokens as trainable tokens that restore self-attention across separately encoded documents.

114 · Our experiment · why KV reuse matters for our agent

Our agent rewrites its history almost every round, so prefix caching re-prefills unchanged text; reusing it could skip ~80% of that work

One event: the prompt before and after a compaction step

the problem
When the history reaches its budget, the harness compacts it: old tool results become short notes and old messages are archived, and past that point it does so almost every round. Every token after the first edit moves, so prefix caching prefills it again although most of it did not change.
the prize
Reusing the moved text skips 79.6% of what prefix caching re-prefills. On Qwen3-32B the next request's first token comes in 90 ms, against 765 ms with prefix caching and 1,097 ms with a full prefill (slide 15).
the runs
500 live runs on 10 real Python codebases × 6 tasks; Qwen3-32B (vLLM 0.29) produced them and Qwen3-8B replays the same events; 683 compaction events

14Result · 4 · which tokens to re-prefill

Which tokens you re-prefill matters more than how many: the first tokens of each moved block beat both high-deviation and random picks

EPIC: first tokens of each moved blockCacheBlend: highest deviationrandom

Why the first tokens win

  • A moved block is a stretch of history that survived the compaction and moved as one piece. Each one starts right where the compaction deleted or replaced text.
  • So a block's first tokens were computed right after text that is now gone: their cached KV is the most out of date.
  • CacheBlend partly finds them. 14–16% of its picks fall in a block's first 32 tokens, 3.2–3.5× what random picks would give (only 4.4% of moved tokens sit there).
  • But it spreads the rest thin: its picks form about 427 separate little pieces per event, where EPIC re-prefills 4 solid ones, the start of each block.
  • At equal budgets EPIC keeps more next rounds identical to full prefill (events where only that arm matches): 47 vs 20 on 32B and 42 vs 22 on 8B for EPIC 32 vs CacheBlend 5%; 60 vs 33 and 52 vs 20 for EPIC 128 vs CacheBlend 15%.

Cost: EPIC 128 re-prefills 308 tokens per event on average. On 200 of the events on an H200, that adds 27 ms (median) to shift RoPE's 90 ms on Qwen3-32B, where full prefill takes 1,097 ms (slide 15).

16TL;DR

Gluing cached pieces loses context and keeps old positions; re-prefilling each piece's first tokens repairs most of it, cheaply

1The KV cache and prefix cachingAttention is a soft lookup over earlier tokens' keys and values; keeping them makes each new token cost one step (144–256 KiB per token on Qwen3). vLLM and SGLang reuse them only for an exact prefix, so one early edit re-prefills everything after it.
2Why gluing breaksTwo reasons. Prefilled apart, B never attends to A (together, 47–95% of B's attention goes to A). And RoPE can be re-rotated exactly only at layer 0; in layers 1 to n−1, the old position is baked into the hidden states.
3One storyline, three papersCacheBlend: attention is sparse, so re-prefill the ~15% that deviate most. EPIC: those few tokens are each chunk's first tokens (attention sinks), so re-prefill the first k. KVLink: first tokens still carry their own meaning, so add trained link tokens that read and summarize all earlier documents (needs fine-tuning).
4Our agent experimentCompaction moves unchanged text, so prefix caching re-prefills it. Shift RoPE skips ~80% of that work (Qwen3-32B's first token in 90 ms, against 765 with prefix caching and 1,097 with full prefill) but changes ~30% of next rounds and costs 11.5 points on long copies (32B) and 19.3 on admitting what is gone (8B). EPIC 128 (11% re-prefilled) repairs both and roughly halves KL, adding 27 ms on Qwen3-32B; CacheBlend repairs only the copy cost, for 3.5–5× EPIC's added time; a random 15% repairs neither.

Not covered: staleness compounding over many compactions in a row (we measured one step), and throughput under concurrent load (we timed one request at a time).
